# freenove-esp32s3-voice

Freenove ESP32-S3 (N16R8) with an INMP441 microphone and a MAX98357A
amplifier. Sofia's board; it replaces the ESPHome node `esp32-freenove`.

## Wiring

### INMP441 microphone — already built

Pins inherited from `~/esphome/esp32-freenove.yaml`, so nothing needs rewiring.

| INMP441 | ESP32-S3 |
|---|---|
| WS / LRCLK | GPIO13 |
| SCK / BCLK | GPIO12 |
| SD / DIN | GPIO11 |
| VDD | 3V3 |
| GND | GND |
| **L/R** | **GND** |

**The L/R pin must go to ground.** Left floating, the channel comes out mute:
the ESP32 boots, everything reports healthy, and the assistant simply hears
nothing. It is a silent failure that has cost time once already. That is why
the code pins `I2S_STD_SLOT_LEFT` on the codec instead of using the default
stereo.

### MAX98357A amplifier — pending

Pins picked from the free ones. **Avoid GPIO 26–37**: on the N16R8 module they
are taken by the flash and the octal PSRAM.

| MAX98357A | ESP32-S3 |
|---|---|
| BCLK | GPIO15 |
| LRC | GPIO16 |
| DIN | GPIO7 |
| VIN | 5V |
| GND | GND |
| SD | not connected (stays enabled) |

With no speaker attached the firmware still works: it listens and streams, and
the returning audio is lost into an unloaded amplifier.

## Why simplex I2S

Microphone and speaker on separate buses. Input runs at 16 kHz and output at
24 kHz; sharing a bus would force them to match and to resample.

## Differences from `bread-compact-wifi`

That board is the canonical INMP441 + MAX98357A example, but it uses different
pins and **requires an OLED display** (`#error` if none is selected). This one
started from `doit-s3-aibox`, which has no display either — swapping its PDM
codec for the I2S the INMP441 needs.

## What survives from the previous system

The blue LED on GPIO2 still shows state. What is **not** ported is the session
logic, the echo filter or the Whisper hallucination filter: all of that moves
to the server. See `docs/decisions/0001-salir-de-esphome.md`.

## GC9A01 display (240x240, round, SPI)

| Module pin | GPIO | Where it is on the Freenove |
|---|---|---|
| VCC | 3V3 | very top, left column |
| GND | GND | very bottom, right column |
| SCL | 42 | right column |
| SDA | 41 | right column |
| DC | 40 | right column |
| CS | 39 | right column |
| RST | 38 | right column |

The five signals sit on **consecutive pins down the right column**, in the same
order they leave the module, so the wiring is a straight run with no crossings.
None of them is a strapping pin. 39–42 are also the pinned JTAG, but the
ESP32-S3 uses JTAG over USB, so they are free.

The module is a **1.28" TFT VER1.0, 240x240, GC9A01 IC**, with **7 pins**: no
BLK. The backlight is hardwired inside, fed by the board's own 3.3 V regulator
(the SOT-23 marked 662K), so `DISPLAY_BACKLIGHT_PIN` stays `GPIO_NUM_NC` and no
GPIO is spent on it. There is no way to dim it from software either.

Free pins: audio takes 7, 11, 12, 13, 15 and 16, and the LED takes 2. On the
N16R8, GPIO 26–32 (flash), 33–37 (octal PSRAM), 19 and 20 (USB) and 43 and 44
(serial console) are off limits as well.

Two deliberate differences from the upstream reference board
(`bread-compact-wifi-lcd`):

- **RES on 39, not on 45.** 45 is a strapping pin on the ESP32-S3: it selects
  the flash voltage, and a pull-up resistor on the module can leave the board
  unable to boot.
- **SPI at 20 MHz, not 40.** A precaution taken because of the breadboard
  wiring, never verified: 40 MHz was not tried and no glitches were seen. It
  costs animation speed — see the comment in `freenove_esp32s3_voice.cc`.

`vendor_config` is not passed either: the reference board's init commands are
for a GC9107, and there they are assigned after the panel is created, so they
never take effect at all.

## The face

The face is **drawn**, frame by frame, and shipped as PNG bytes. It is not
built from LVGL primitives and it is not the firmware's stock emoji, which is a
square PNG in the middle of a round screen — small, yellow, and one fixed image
per emotion.

The frames live in `face/frames/` in the project repository and are turned into
C arrays by `face/export_esp32.py`, which writes `eyes_png.[ch]` and
`mouth_png.[ch]` next to this file. They travel as PNG rather than raw RGB565
because the firmware carries the lodepng decoder: about 9 KB per frame instead
of 115 KB. **Do not edit the generated files by hand** — edit the images and
re-run the exporter.

Twelve eye frames: two colour variants (white iris at rest, green while
listening) times six poses — centre, left, right, down, half-open and closed.
Nineteen mouth frames: eight opening steps for lip sync, and eleven gesture
mouths. The emotion-to-gesture table is generated by the exporter too, so the
firmware holds no second copy of it.

`DrawnFace` in `freenove_esp32s3_voice.cc` is what picks a frame. What it still
computes at runtime:

- **Lip sync from the real audio.** `LevelMeteringCodec` overrides
  `OutputData` and publishes the level of what is actually leaving the speaker.
  The mouth opens when sound comes out, not when the server announces a reply.
- **Blinking**, every 5 to 14 s, with the interval drawn again on each firing so
  it does not beat like a metronome. The half-open frame appears on the way
  down and on the way up; that is what tells a blink from a cut.
- **Gaze**, every 2.5 to 9 s, two glances in three returning to the centre.
- **Sleeping eyes.** Out of a session the eyes are closed; they open when the
  conversation starts. The rule is written in terms of what IS a session —
  connecting, listening, speaking — because there are more out-of-session
  states than STANDBY alone.

Only one eye gesture is approved so far (Normal), so emotion shows in the
mouth. More gestures are a matter of drawing them and exporting.

### The mistake that cost a boot loop

`SetTheme()` writes to `mute_label_`, `battery_label_` and `network_label_`,
which **do not exist until `SetupUI()` creates them**. Calling it from the
board constructor writes through null pointers and the board reboots in a
loop. Anything touching LVGL objects belongs inside `SetupUI()`, after calling
the parent's. The upstream `otto-robot` board does exactly that and says so in
a comment.
